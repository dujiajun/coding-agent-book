# 7.3 风险、伦理与展望

> 本章导览：Coding Agent 带来的真实风险与应对边界，以及从源码结构中能读到的技术演进方向。本章是全书的收束——机制讲完了，剩下的是选择。

## 失业焦虑与现实

先直面最常见的问题：Agent 会让程序员失业吗？

从本书的解剖结果看，Coding Agent 的能力边界相当清晰。它擅长的是**目标明确、验收可判、路径可探索**的工程任务：改一个有测试保护的模块、修一个可复现的 bug、按计划执行重构。它在这些任务上的速度优势是数量级的。它不擅长的同样是明确的：定义"什么问题值得解决"、在目标冲突时做取舍、为没有先例的系统设计承担责任的架构。前者正在快速商品化，后者依然稀缺。

更符合现实图景的不是"程序员 vs Agent"，而是**会用 Agent 的程序员 vs 不会用的程序员**——7.2 节的技能栈就是分界线。历史上编译器、开源软件、云计算都曾被视为"取代程序员"的威胁，实际结果都是抬高了行业的天花板、改变了岗位的形态。Agent 大概率延续这个模式，但有一个真实的区别值得清醒：这次被压缩的不再只是体力环节（汇编、样板代码），还包括部分初级脑力环节（查资料、写常见功能）。入行者需要更快地走到"能定义问题、能做判断"的层级，学徒期的缓冲变短了——这是行业要共同面对的转型成本，不是一句"新工具而已"能带过的。

对个体而言，理性的策略不是抗拒工具，而是尽快把自己放到人机协作中更有杠杆的位置上：规约的作者、评测的设计者、最终质量的把关人（7.1、7.2 节）。

## 安全与伦理边界

技术风险在 6.4 节已经系统讨论过（prompt injection、供应链、权限绕过），这里补充三个更"软"但同样真实的边界。

**数据与隐私。** Agent 天然是高权限程序：读代码库、发网络请求、调云端模型。你的代码、乃至代码里的密钥和业务数据，会进入模型供应商的处理范围。工程上的应对在书里都有原型——最小权限模式、deny 规则、敏感信息不入库的日志纪律（6.1 节的脱敏设计）——但组织层面还需要明确的数据分级策略：哪些仓库允许接云模型，哪些必须本地部署（4.4 节的能力正是为此准备的）。

**自动化武器的平民化。** 本书的机制（批量 SubAgent、定时任务、自主长跑）与安全研究者手中的自动化只有一线之隔。6.4 节的系统提示词安全声明不是装饰：授权的安全测试可以做，破坏性用途必须拒绝。对工具作者，这意味着把滥用成本设计进系统（权限默认收紧、审计日志不可绕过）；对使用者，意味着对自己的自动化保持与人相同的责任标准——让十个 Agent 去爬别人的站点，和亲自去爬，在伦理上没有区别。

**责任与透明。** Agent 产出的代码进入了生产系统，"这是 AI 写的"不能成为质量事故的免责理由（7.1 节）。同时，组织有理由知道代码的来源构成。可行的做法是把 Agent 参与度变成工程事实的一部分：提交记录、评审记录、评测通过率——这些都是现成的载体。透明不是为了惩罚，而是为了让"人机协作代码"的质量模型与责任模型同步演进。

## 技术演进趋势

最后看方向。以下判断不靠预言，而是从本书解剖的这套源码的结构性压力中读出来的——每个尚未补齐的短板，都是下一阶段的演进方向。

**沙箱会回来。** 5.3 节留下的"负空间"（接口在、执行端不在）是最明确的信号：当 Agent 从辅助工具变成自主执行者，OS 级隔离（文件系统视图、网络出口、进程权限）就是刚需。合同已经写好（`ExecutionSandboxPolicy`），缺的是跨平台的执行端实现。教学上你已经知道为什么难：Windows/macOS/Linux 的隔离原语完全不同。

**记忆会走向检索与生命周期管理。** 2.3 节的"索引 + 文件 + 轮末提取"是文本时代的方案。当会话数量和记忆条目增长，纯靠常驻索引的召回会遭遇规模天花板——但方向不是回到向量库，而是给记忆加上完整的生命周期：来源溯源（已经有了 originSessionId）、过期、冲突合并、跨项目迁移。

**评测与可观测会成为一等公民。** 6.2 节如实写了现状：评测基建是脚本和内部工具，不是产品。随着 Agent 承担的任务越来越关键，"这次的改动让 Agent 成功率从 82% 掉到 71%"必须成为 CI 里的一条红线。轨迹格式、评测 harness、回归对账会标准化——就像单元测试框架在二十年前经历的那样。

**多 Agent 协作的协议化。** 本书的 SubAgent（2.5）是单向委派：父派活、子交差、 SendMessage 打补丁。动态工作流（5.7）迈出了编排的一步，但 agent 之间的消息协议、能力协商、结果仲裁仍处于"约定俗成"阶段。MCP 统一了 Agent 与工具的接口（2.2 节），Agent 与 Agent 之间的"MCP 时刻"还没到来，但需求已经真实存在。

**模型能力对架构的反作用。** 本书所有机制都建立在"模型要靠多轮工具调用才能完成任务"的假设上。长上下文、更长的稳定推理、原生计算机操作，每项能力提升都会重新划分哪些机制该留在 runtime、哪些可以下放到模型：压缩策略随窗口变大而宽松，检索随记忆能力增强而简化。Agent 开发者需要持续回答一个问题——**哪些复杂度是模型暂时背不动的？** 这正是这套 runtime 的存在理由，也是它永远的迁移对象。

## 结语

这本书从一个简单的循环开始：请求模型，执行工具，回灌结果，直到模型不再调用工具（2.1 节）。然后我们用三十多节的篇幅看到，让这个循环在真实世界里可靠运转需要什么——上下文要经营（2.3）、历史要压缩（2.4）、失败要分层兜底（6.3）、权限要问人（5.3）、行为要可观测（6.1）、质量要有评测（6.2）。

没有一行魔法。你已经在 tinycode 里亲手写过其中最重要的部分，也在 ZCode 的源码里见过它们生产级的形态。Agent 开发不是一门新的学科，而是软件工程的老原则——最小权限、幂等、可观测、契约优先——应用在一个新的执行主体上。原则是旧的，主体是新的，所以每一章都有新的权衡要做。

接下来最好的学习方式，是挑一个你在意的问题动手：给 tinycode 加一个你在本书里没见到的机制；或者把 ZCode 的某个模块读穿，对照本书的章节画出你自己的架构图。工具会迭代，模型会换代，但理解了机制的人，换多少次船都上得去。
