# 7.2 程序员的新技能栈

> 本章导览：当"把需求翻译成代码"不再是瓶颈，程序员的比较优势转移到哪里——本章把全书出现的工程实践整理成一份可刻意练习的技能清单。

读完前六章你会发现：本书讲的所有机制，反过来就是一份"与 Agent 协作所需的能力清单"。你不需要会造 Agent 才能用好 Agent，但理解压缩（2.4）、权限（5.3）和评测（6.2）的人，显然比只会写提示词的人走得更远。本章把这些能力整理成四组，按"投入产出比"排序。

## 评估与编排 Agent

这是新技能栈的核心，包含三件相互关联的事。

**第一件：任务分解与委派判断。** 拿到一个需求，先判断它属于哪种执行形态——是 7.1 节的三种工作流中的哪一种：需要规划的大改动、验收清晰的中型任务、还是可自动化的例行工作？再判断上下文策略：一次会话能装下吗（回想 200K 窗口与 166K 阈值，2.4 节）？要不要拆给 SubAgent（2.5 节）做只读探索以免污染主上下文？这些判断直接决定任务成败，而它们依赖你对 Agent 运行时机制的心智模型——这正是本书第一、二部分给你的东西。

**第二件：写规约与写技能。** AGENTS.md、SKILL.md、自定义命令（4.2 节）是新时代的"基础设施代码"。写好它们的能力构成很具体：把团队隐性知识显性化、把触发条件写进 description（"什么时候该用我"比"我是什么"更重要）、用渐进披露控制上下文成本。衡量标准是可复用的次数——一条只解决一次性问题的 prompt 是开销，一条被十次任务复用的 Skill 是资产。

**第三件：设计评测。** "怎么知道 Agent 改好了"是最容易被忽视、复利最高的技能。6.2 节的三层框架可以直接搬用：组件级断言（该调的工具调了吗）、任务级验收（测试过不过）、回归集（改了 prompt 之后老任务还过吗）。哪怕只是给团队维护一个二十条用例的 eval 脚本，也足以把"感觉变好了/变坏了"的争论变成数据。ZCode 用生产轨迹做影子重放（6.2 节）的思路同样值得借鉴：你积累的每一次真实会话，都是明天的回归测试素材。

## 提示工程

本书刻意少用这个词，因为对 Coding Agent 而言，"提示工程"的大部分内容已经工程化了：系统提示词由 runtime 分节构建（2.3 节），指令文件由 AGENTS.md 承载，领域知识由 Skill 注入，任务由 Agent 工具的自包含 prompt 委派。留给手工打磨的部分收敛为三个场景：

- **任务描述**：目标、约束、验收标准、相关文件范围。反模式是过程性 micromanagement（"先打开 A 文件然后……"）和目标缺失（"优化一下这个项目"）。
- **纠偏反馈**：Agent 跑偏时的 steer 消息。有效的纠偏指向**事实**（"测试 X 失败，错误是 Y"）而非情绪（"你做错了"）——工具结果回灌机制（2.1 节）决定了模型对具体错误的响应远好于对笼统批评的响应。
- **Plan 审批与 verifier 设计**：5.2 节的"反馈式拒绝"和 5.4 节的完成审计清单展示了一个原则：**给出可执行的下一步，比给出否定更有用**。你驳回计划时附上理由，Agent 下一轮就少绕一次路。

一个实用的自检问题：当你想写一段长 prompt 时，问自己"这段话是一次性的，还是以后每次都要说？"——是后者，就应该把它搬进 AGENTS.md 或 Skill，而不是继续粘贴。

## 调试与可观测

Agent 参与越多，"系统行为解释权"就越重要。6.1 节的三层观测（结构化日志、trace、Model I/O 轨迹）不只是 Agent 开发者的工具，也是重度使用者排查协作问题的工具。需要练的具体能力：

1. **读轨迹**：从一次不理想的会话里看出"模型在第几步拿到了什么信息、做了什么决定"。traceId 链（6.1 节）是入口，工具调用序列是骨架。
2. **识别失败模式**：对照 6.3 节的失败域全景——是上下文被压缩丢了关键约束？是工具输出被截断（3.4 节的 30KB 上限）？还是权限被拒后模型没拿到足够信息？不同失败有不同的解法（调 compact 策略、放宽权限规则、补 AGENTS.md），对症才能下药。
3. **成本感知**：token 消耗是真实账单。知道哪些操作便宜（缓存命中的重复请求）、哪些昂贵（每次都重新灌大文件、压缩风暴），就能用同样的预算完成更多任务。辅助模型压到最低推理档（1.3 节）这种成本工程思维，同样适用于你选择"这个问题值不值得动用 Agent"。

## 工程审美的价值

最后一组技能最古老，却在这个时代升值最快：**判断什么是好的软件**。

Agent 能生成的代码量呈数量级增长，但"生成的代码该不该留下"的判断标准没有变——模块边界是否清晰、错误处理是否诚实、命名是否表达了意图、有没有为了眼前便利埋下长期债务。这些判断来自多年工程经验的积累，恰恰是模型最难从文本中学到的部分。ZCode 的 AGENTS.md 里那些约束（"错误是一等设计对象""不要用超时掩盖同步问题"）之所以写得出来，是因为有人知道违反它们的代价。

实践上有三个抓手：

- **做 Agent 的规约作者**：把你的工程审美写成 AGENTS.md 的条目和 Skill 的指引，审美就变成了可复制的约束（7.1 节"用规约约束"）。
- **做 review 的最终把关人**：模型写的代码也要过人类的质量关。审 Agent 的 diff 和审同事的 PR 用同一套标准——这本身就是对工程审美的持续训练。
- **保持亲手写代码的能力**：理解循环怎么写（2.1 节）才能判断 Agent 的循环写得对不对。本书带你从零构建一遍 Agent，正是为了让你的判断有根系——**你可以不亲手造它，但你必须造得出它，才能驾驭它**。

把这四组能力放在一张表上：

| 技能组 | 核心动作 | 对应本书章节 |
| --- | --- | --- |
| 评估与编排 | 任务分解、规约设计、评测建设 | 2.3–2.6、4.2、6.2 |
| 提示工程 | 任务描述、纠偏、计划反馈 | 2.1、5.2、5.4 |
| 调试与可观测 | 读轨迹、识别失败模式、成本感知 | 6.1、6.3 |
| 工程审美 | 规约化、review 把关、保持手感 | 5.3、7.1 |

它们共同指向同一个转变：程序员的价值锚点，正在从"我能写出这段代码"迁移到"我能定义、约束并验收这段代码的产生过程"。技能栈变了，职业的内核没变——**用工程方法控制复杂性**，只是现在复杂性多了一个新的来源和一个新的帮手。
